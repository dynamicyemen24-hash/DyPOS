# DyPOS — برنامج التحديث العميق لنظام التصميم وتجربة الاستخدام

> الحالة: RFC / خطة تنفيذ معيارية — لا تُعد هذه الوثيقة إثباتاً على أن التغييرات المرئية أو اختبارات التشغيل قد نُفذت.
> النطاق: POS Vue 3 + Vite + Tailwind، نظام التصميم الحالي في `POS/src/styles/`، المكونات المشتركة، وتجربة البيع والعمل دون اتصال.

## 1. الهدف وحدود السلامة

توحيد واجهات DyPOS حول نظام تصميم عربي أولاً، سريع على أجهزة نقاط البيع منخفضة المواصفات، يعمل دون اتصال، ويحافظ على سلوك البيع والمرتجعات والطباعة والصلاحيات وعزل المستأجرين. نستلهم مبادئ التصميم العامة الموثقة في SAP Fiori، Microsoft Fluent 2 وOracle Redwood؛ لا ننسخ شيفرات أو أصولاً أو علامات تجارية محمية، ولا نضيف اعتماداً جديداً لمجرد التشابه البصري.

**قاعدة الإصدار:** لا إعادة كتابة شاملة، ولا استبدال جماعي للمكونات، ولا تعديل في قواعد الأموال/الضريبة/المزامنة أثناء تجميل الواجهات. كل ترحيل صغير، قابل للمراجعة والرجوع، ومقاس باختبارات.

## 2. معايير غير قابلة للتفاوض

1. **العربية وRTL افتراضياً:** استخدم `dir` وخصائص CSS المنطقية (`margin-inline`, `padding-inline`, `inset-inline`, `border-inline`) بدل افتراض اليمين/اليسار. اختبر العربية والإنجليزية، الأرقام، العملات، والباركود.
2. **تشغيل البيع دون شبكة:** لا تجعل عرض المكونات أو التنقل أو إتمام البيع معتمداً على خادم المزامنة. لا تغيّر سياسة المزامنة الافتراضية أو مسارات الاسترداد.
3. **صدق البيانات:** لا بيانات وهمية أو أرقام تجريبية في واجهات الإنتاج. عند فشل المصدر، اعرض حالة خطأ/غير متاح مع إجراء استرداد، لا صفراً مختلقاً أو قائمة فارغة توحي بالنجاح.
4. **لمس أولاً:** الحد الأدنى لهدف اللمس 44×44 CSS px، ومسافات تمنع النقر الخاطئ على شاشة كاشير مزدحمة.
5. **إتاحة قابلة للاختبار:** تباين WCAG 2.2 AA، تركيز مرئي، تشغيل لوحة المفاتيح، أسماء وصول للأيقونات، أخطاء مرتبطة بالحقول، وعدم الاعتماد على اللون وحده.
6. **لا تغيير صامت للعقود:** حافظ على أسماء الأحداث والـ props، مفاتيح التخزين، عقود API، الطباعة، واختصارات لوحة المفاتيح. أي تغيير تعاقدي منفصل ومختبر.
7. **الديون التقنية مرئية:** لا تُرفع حدود أحجام الملفات، ولا تُضاف استثناءات فحص، ولا تُخفى تحذيرات. الاستخراج يسبق توسيع الملفات الكبيرة.

## 3. طبقات نظام التصميم

### المستوى A — رموز أساسية (Foundation tokens)

المصدر المعتمد: `POS/src/styles/design-tokens.js` مع آلية الربط الحالية في `theme-manager.js`. قبل إضافة أسماء جديدة، احصر الرموز الموجودة واربط المرادفات بها بدلاً من إنشاء مصدر موازٍ.

- **اللون الدلالي:** `surface`, `surface-raised`, `text-primary`, `text-muted`, `border-subtle`, `brand`, `success`, `warning`, `danger`, `info`, `focus-ring`. لا تستخدم لون الحالة كزخرفة.
- **المسافات:** مقياس من 4px (4، 8، 12، 16، 20، 24، 32، 40) مع استثناءات موثقة فقط.
- **الخطوط:** Cairo للعربية حيث هو معتمد بالفعل؛ سلم واضح للعناوين والنصوص وبيانات الجداول. استخدم أرقاماً ثابتة المحاذاة للأرصدة والمجاميع.
- **الأشكال والارتفاع:** درجات محدودة لنصف القطر والظلال؛ لا ظلال ثقيلة على كل بطاقة.
- **الحركة:** قصيرة وهادفة، تحترم `prefers-reduced-motion`، ولا تؤخر الدفع أو استجابة اللمس.
- **الكثافة:** `comfortable` للإدارة و`compact` لقوائم المخزون والجداول، مع بقاء أهداف اللمس قابلة للاستخدام.

### المستوى B — عقود المكونات المشتركة

المكونات الأساسية تُراجع في `POS/src/components/common/` ومجلدات المكونات القائمة قبل إنشاء بديل.

| الفئة | العقد المطلوب |
|---|---|
| Button | الأنواع primary/secondary/tertiary/danger، حالات loading/disabled، منع الإرسال المكرر، تسمية واضحة |
| TextField / Search | label دائم، وصف/خطأ مرتبط، مسح قابل للوصول، عدم فقدان التركيز بعد التحديث |
| Select / Combobox | لوحة مفاتيح، نتائج فارغة/فشل تحميل منفصلة، اتجاه RTL صحيح |
| Dialog / Drawer | احتجاز التركيز، Escape عند السماح، إعادة التركيز للمُشغّل، تأكيد للعمليات المدمرة |
| Badge / Status | حالات دلالية ثابتة مع نص/أيقونة، لا لون فقط |
| DataTable | حالة تحميل/فراغ/فشل منفصلة، فرز معلن، رؤوس دلالية، تمرير مناسب للشاشات الصغيرة |
| Toast / InlineAlert | رسائل عربية واضحة، مدة مناسبة، إجراء استرداد عند الحاجة، لا أخطاء تُختفى دون أثر |
| EmptyState | يوضح سبب عدم وجود البيانات ويقدم إجراءً ممكناً فقط إذا كان مدعوماً فعلاً |
| Skeleton | يستخدم فقط عندما يكون التحميل جارياً؛ لا يُستخدم كبديل عن حالات الفشل |
| Money / Quantity | تنسيق موحد من أدوات التنسيق الحالية؛ لا حساب ضريبة أو إجمالي داخل مكوّن عرض |

لا يُضاف مكوّن إلى barrel عام إلا إذا كان مستخدماً فعلاً؛ حافظ على بوابة dead exports.

### المستوى C — أنماط الصفحات

- **Shell:** عنوان صفحة واضح، مسار تنقل عند الحاجة، مساحة محتوى مرنة، وحالة اتصال/مزامنة غير مزعجة لكنها صادقة.
- **قوائم الإدارة:** بحث وفلاتر قابلة للمسح، أفعال صفوف متوقعة، ترقيم/تحميل متسق، وحالات بيانات موحدة.
- **النماذج:** تقسيم منطقي، حفظ/إلغاء واضحان، تحقق مبكر ورسائل استرداد عربية.
- **لوحات المؤشرات:** لا تعرض أرقاماً ثابتة أو مخزنة كأنها مباشرة؛ أظهر وقت التحديث واكتمال البيانات عند الحاجة.
- **الحالات العامة:** loading، empty، error، offline، stale، permission-denied، partial-data لكل شاشة تعتمد على مصدر بيانات.

## 4. معيار واجهة الكاشير (مسار P0)

يظل المسار المرئي الأساسي: **بحث/مسح → إضافة → مراجعة السلة → الدفع → تأكيد النتيجة → طباعة/إعادة طباعة**.

- لا تُزاح السلة أو الإجمالي النهائي بفعل لوحات جانبية غير أساسية.
- يبقى الإجمالي النهائي ووسيلة الدفع والإجراء الأساسي مرئية على أحجام الشاشات المدعومة.
- المسح بالباركود يدعم التركيز والاستعادة بعد إضافة الصنف، ويعلن نتيجة غير موجود/مكرر/تعذر قراءة دون تعطيل الإدخال اليدوي.
- تعطيل زر الدفع أثناء المعالجة مع حماية idempotency الموجودة؛ الفشل يوضح هل تم حفظ البيع أم لا قبل السماح بإعادة المحاولة.
- خصم/مرتجع/إلغاء عملية تتطلب عرض أثرها المالي وتأكيداً مناسباً للصلاحية.
- عند عدم الاتصال، توضح الواجهة ما هو محفوظ محلياً وما ينتظر المزامنة؛ لا تدّعي أن بيانات السحابة محدثة.
- الطباعة فشل قابل للاسترداد: عرض نتيجة البيع مستقلة عن نجاح الطابعة، مع إجراء إعادة طباعة لا ينشئ فاتورة جديدة.

## 5. استراتيجية التوافق البصري والتقني

1. جرد الرموز، المكونات، الأنماط المكررة، الصفحات ذات أعلى كثافة، والاختبارات القائمة؛ لا تفترض أن مكوّناً مفقود لأن اسمه غير واضح.
2. اختر مكوّناً مشتركاً واحداً وطبّق عليه التوكنز مع اختبارات سلوكية؛ لا تستبدل المكونات دفعة واحدة.
3. طبّق الأنماط على صفحة منخفضة المخاطر أولاً، ثم قائمة/نموذج، ثم شاشة الكاشير بعد قياس أثر الأداء.
4. أبقِ الفئات القديمة كطبقة توافق مؤقتة إذا كانت مستخدمة، وأزلها فقط بعد إثبات عدم وجود مستهلكين.
5. لا تضف مكتبات أيقونات أو مكونات أو رسوم بيانية إضافية إذا كان الموجود يغطي الاستخدام؛ أي اعتماد جديد يحتاج تبريراً لحجم الحزمة والصيانة والأمان.
6. احترم CSP الصارم، ولا تضف `unsafe-inline` أو تحميل خطوط/أصول من مصادر غير معتمدة.

## 6. سجل الديون التقنية — بوابة قبل كل دفعة

| الرمز | الخطر | المعالجة المطلوبة | معيار الإغلاق |
|---|---|---|---|
| DS-01 | تعدد مصادر الحقيقة للرموز | تدقيق `design-tokens.js` و`theme-manager.js` وCSS وربط المرادفات | لا قيمة دلالية متعارضة لنفس الغرض |
| DS-02 | تكرار أنماط المكونات | جرد الأنماط قبل إنشاء مكون جديد | إزالة تكرار مقاس أو توثيق الاستثناء |
| DS-03 | ملفات Vue كبيرة | استخراج composables/مكونات صغيرة قبل إضافة سلوك | حدود الحجم لا ترتفع واختبارات الصفحة خضراء |
| DS-04 | RTL غير شامل | اختبار اتجاهي لكل مكون متأثر | لا اعتماد جديد على left/right في التغييرات |
| DS-05 | حالات فشل غير واضحة | فصل empty عن error وoffline وpartial | لكل فشل إجراء استرداد مناسب |
| DS-06 | وصولية غير متحققة | اختبارات لوحة مفاتيح واسم/تركيز/تباين | معايير الوصول أعلاه قابلة للتحقق آلياً ويدوياً |
| DS-07 | كلفة الحزمة والأداء | قياس build وbundle ووقت تفاعل الكاشير | ميزانية الحزمة الحالية لا تتراجع |
| DS-08 | انحراف العقود | فحص props/events/storage/API قبل refactor | اختبارات العقد والتكامل خضراء |

هذا السجل يحدد مخاطر يجب قياسها، وليس ادعاءً بأن كل مشكلة موجودة فعلاً. تُرفق القياسات وروابط الاختبارات بكل تغيير.

## 7. خطة الإطلاق على دفعات

### P0 — جرد وحماية (قبل تعديل المظهر)
- تسجيل SHA الأساس، قراءة اختبارات الواجهة والتصميم، قياس build والحزمة وأحجام الملفات.
- تحديد مكونات مشتركة موجودة بالفعل، وإزالة التكرار فقط بعد فحص المستهلكين.
- تسجيل لقطات مرجعية لمسارات البيع/المرتجع/الطباعة/العمل دون اتصال.

### P1 — الأساس المرئي
- توحيد الألوان والمسافات والطباعة والتركيز والاتجاه عبر الرموز الحالية.
- توحيد حالات التحميل/الفراغ/الفشل والتنبيهات في المكونات المشتركة.
- اختبارات tokens/theme/RTL/accessibility وعدم وجود بيانات وهمية.

### P2 — المكونات والأنماط
- ترحيل زر/حقل/حالة/حوار واحداً في كل دفعة.
- إزالة المكونات غير المستخدمة فقط عندما تؤكد بوابة dead exports ذلك.
- إضافة اختبارات props/events والتركيز ولوحة المفاتيح.

### P3 — الصفحات
- إدارة المنتجات والعملاء والمخزون والتقارير على دفعات صغيرة.
- الكاشير أخيراً بعد نجاح الاختبارات المرجعية وتأكيد عدم تأثر مسار البيع.
- مقارنة أداء وحزمة قبل/بعد؛ لا يُقبل تراجع غير مبرر.

### P4 — الحوكمة المستمرة
- إضافة صفحة توثيق للمكونات المستخدمة فقط، وأمثلة RTL وdark/light إن كان الثيم مدعوماً.
- كل PR يتضمن: المشكلة، الملفات، السلوك المحفوظ، الاختبارات، قياس الحزمة، الدين التقني الذي أُغلق أو فُتح، وخطة الرجوع.

## 8. بوابات القبول

نفّذ الأوامر وفق `AGENTS.md` وملفات المشروع الفعلية؛ لا تعتمد على أعداد اختبارات قديمة دون قياسها:

- `cd POS; npm run test:run`
- `cd POS; npx biome check src/<touched-files> tests/<related-tests>`
- `cd POS; npm run typecheck`
- `cd POS; npm run build`
- `cd POS; npm run size`
- من الجذر: اختبارات الخادم، `npm run parity` و`npm run contract` إذا مس التغيير العقود أو التكامل.
- اختبارات يدوية على جهاز لمس صغير وشاشة عريضة، RTL/LTR، شبكة مفصولة، طابعة غير متاحة، صلاحية مرفوضة، وبيانات جزئية.

**لا يُعلن النجاح** ما لم تُشغّل البوابات فعلياً. لا تدمج التغييرات التي تؤثر في البيع أو الأموال أو المخزون أو المزامنة دون اختبارات الانحدار ذات الصلة.

## 10. التوافق الشامل: أجهزة ومتصفحات ولغات

### الأجهزة والاستجابة
- التصميم يبدأ من عرض 320px ولا يفترض فأرة أو hover؛ كل إجراء أساسي قابل للمس ولوحة المفاتيح.
- اختبر 320/360/390px للهواتف، 768px للأجهزة اللوحية، و1024/1280px فأعلى لنقاط البيع المكتبية، مع تكبير الصفحة ولوحة المفاتيح الافتراضية وتدوير الشاشة.
- لا تعتمد على User-Agent وحده لتصنيف الجهاز؛ اجمع عرض مساحة العرض ونقاط اللمس وقدرات الجهاز المتاحة مع fallbacks عند غياب APIs.
- راعِ safe-area على أجهزة iOS، وارتفاع viewport المتغير في المتصفحات المحمولة، والاتصال البطيء، والذاكرة المحدودة، والعمل دون اتصال.
- لا يُعلن دعم كل متصفح لمجرد استخدام CSS حديث: ثبّت مصفوفة إصدارات دعم معلنة، واختبر Chromium/Edge وFirefox وSafari وSafari على iOS، وأجهزة Android WebView الشائعة. استخدم progressive enhancement وميزات بديلة عند غياب API.
- حافظ على الطباعة وقارئات الباركود ولوحات المفاتيح وماسحات الإدخال كأجهزة طرفية أساسية؛ اختبرها فعلياً لأن محاكاة المتصفح لا تكفي.

### تعدد اللغات والتوطين (i18n/l10n)
- العربية هي اللغة الافتراضية الحالية، لكن كل واجهة جديدة يجب أن تفصل النص عن التخطيط؛ لا تضف نصوصاً ثابتة داخل المكونات عندما تكون قابلة للترجمة.
- الاتجاه خاص باللغة لا بالمستخدم: العربية RTL والإنجليزية LTR؛ لا تستخدم قلباً شاملاً للأيقونات أو الأرقام، واستعمل خصائص CSS المنطقية.
- لا تُعلن لغة مدعومة قبل اكتمال قاموسها الأساسي ورسائل التحقق والأخطاء والطباعة. عند غياب ترجمة، استخدم fallback معروفاً وسجّل المفتاح المفقود دون إظهار مفاتيح تقنية للمستخدم.
- استخدم Intl.NumberFormat وIntl.DateTimeFormat لتنسيق الأرقام والتواريخ والعملات حسب locale، مع إبقاء الحسابات المالية ودقة التخزين مستقلة عن التنسيق البصري.
- اختبر النصوص الطويلة، الجمع والمفرد، التواريخ والأرقام المختلطة، أسماء المنتجات، الاتجاهات داخل النص، وتغيير اللغة أثناء العمل دون إعادة تحميل الصفحة.
- يجب أن يظل تبديل اللغة قابلاً للاستخدام إذا فشل التخزين المحلي أو انقطعت الشبكة؛ تفضيل اللغة محلي أولاً، وتحميل الترجمات الإضافية تحسين غير حاجب.

### بوابة القبول الإضافية
لا يُعلن التوافق الشامل إلا بعد نتائج مصفوفة أجهزة/متصفحات موثقة، واختبار اللغات المتاحة فعلياً، وتأكيد RTL/LTR وإمكانية الوصول والعمل دون اتصال. أي متصفح أو لغة لم تُختبر تُذكر كقيد صريح بدلاً من الادعاء بدعم مطلق.


## 11. جرد الموجود والفجوات بعد فحص الشيفرة

هذا الجرد مبني على الملفات الموجودة في `POS/src/components` وقت المراجعة؛ لا يُنشأ بديل لمكوّن قائم لمجرد اختلاف الاسم.

### الموجود ويجب إعادة استخدامه

- **الأزرار:** `ActionButton` من حزمة `dypos-ui` هو الأساس الموحد، و`Button` و`DyButton` و`IconButton` توافقات/واجهات انتقالية. لا نضيف `BaseButton` جديداً.
- **السطوح:** `DyCard` و`DyPanel`؛ لا نضيف بطاقة عامة أخرى.
- **التنبيهات:** `Toast.vue` و`useToast` للتنبيهات العابرة؛ المطلوب المتبقي هو نمط تنبيه مضمّن داخل الصفحة، لا Toast ثانٍ.

### الفجوات التالية — لا تُنشأ قبل فحص مواضع الاستخدام

1. **P0 — FormField:** توسيع اعتماده تدريجياً على الحقول المتكررة، بعد فحص اختلافات السلوك والاختبارات؛ لا إعادة كتابة كل النماذج دفعة واحدة.
2. **P1 — InlineAlert:** أُضيف المكوّن واختباراته؛ الخطوة التالية هي ترحيل مواضع متكررة محددة بعد مراجعة السياق، لا استبدال كل الرسائل آلياً.
3. **P1 — Dialog foundation:** لا تنشئ `BaseDialog` قبل مراجعة أنماط الحوارات الحالية والتركيز وEscape وقفل التمرير وعودة التركيز؛ الأفضل توحيد الأساس الموجود بدلاً من إدخال نظام حوار موازٍ.
4. **P2 — Responsive data views:** حسّن `WorkDataGrid` و`ReportTable` الحاليين للجوال ولوحة المفاتيح والتكبير، بدلاً من إنشاء جدول ثالث. لا تحوّل الجدول إلى بطاقات إلا عندما تبقى العلاقات والإجراءات واضحة.
5. **P2 — Locale formatting:** راجع استخدام `Intl` الحالي ووحّد أدوات التنسيق فقط إذا ثبت تكرار المنطق؛ لا تكرر حسابات المال أو تقريب العملة داخل مكوّن عرض.
6. **P3 — Browser/device gates:** أضف اختبارات حقيقية أو E2E للمقاسات وRTL/LTR والطباعة والماسح والعمل دون اتصال؛ اختبار jsdom وحده لا يثبت التوافق مع Safari أو أجهزة نقاط البيع.

كل مكوّن جديد يجب أن يكون له مستهلك فعلي واختبار مناسب؛ لا تصدّره من barrel إن لم يكن مستخدماً. لا يُعتبر التغيير مُتحققاً منه حتى تمر اختبارات POS وBiome وtypecheck والبناء وفحص حجم الحزمة.
